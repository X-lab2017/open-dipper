# 共建社区 / Community — 产品设计 v0.1

**设计提案，尚未实现或改名上线。** 2026-10-27。当前站点仍使用“参与共建”，路由为 `#contribute`。本方案承接[情报室流程](INTELLIGENCE_WORKFLOW.md)，保留现有主导航与前三个模块。

## 命名与定位

建议导航：**全球观测｜AI 雷达｜开源星系｜Agent 情报室｜共建社区**。

| 候选 | 判断 |
| --- | --- |
| 共建社区 / Community（建议） | 覆盖用户反馈、资料、案例、开发和公开成果；无需懂代码也能进入 |
| 参与共建 / Contribute（现名） | 动作明确，适合按钮；作为整个空间的名称略像说明页 |
| 共创中心 / Co-creation | 容易被理解为内容创作或商业孵化，与研究功能产生重叠 |

页面主标题建议“让一次使用，推动下一次改进”。第一目标不是展示贡献人数或吸引提交量，而是让用户知道：**我能贡献什么、交给谁、怎样知道有结果**。GitHub 是第一版协作记录源，不重复建立一个没有后端的任务系统。

## 一屏设计：从我的意图开始

桌面采用紧凑 **左入口 / 中央行动与任务 / 右说明和进展**，沿用站内明暗、双语、键盘与减少动态效果规范。主内容优先，不铺大幅宣传区。手机按入口→行动→说明顺序，隐藏内容可明确展开。

| 区域 | 首版内容与交互 | 成功结果 |
| --- | --- | --- |
| 页首 | 标题、一句解释、主按钮“反馈使用体验”；次按钮“查看共建成果” | 两步内找到适合自己的入口 |
| 左侧 | 反馈体验、贡献资料、参与开发三个入口；默认反馈体验 | 按意图选择，不要求先识别自己的身份 |
| 中间：反馈体验 | 任务、遇到的情况、期望结果；已有反馈先看 #35，独立缺陷转现有表单 | 找到已有讨论或打开正确表单 |
| 中间：贡献资料 | 来源 URL、对象、日期、补充/纠错说明；可选“贡献案例”走现有需求表单 | 说明证据和可复用范围；未经审核不进入正式情报 |
| 中间：参与开发 | 阅读贡献指南和 AGENTS；入口到当前 issues / PR；将设计、术语、数据核验、测试、代码并列 | 人或 Agent 找到一个可协商范围的任务 |
| 右侧 | 当前选择的提交要求；“接下来会发生什么”；已有讨论/PR 链接 | 提交前知道谁审阅、如何追踪 |
| 第二屏（可选） | 精选已发布改进：问题→PR→检查/发布→回到功能；支持与合作置于页尾 | 使用者能回到实际改进后的产品 |

第一版任务入口链接到 GitHub 的实时列表，不在静态页面伪造“可领取/处理中”卡片。精选成果可由维护者维护小型有日期的清单，列明核对时间和原始记录；不显示无法持续核实的实时贡献人数、响应时长或完成率。没有记录显示空状态，加载失败保留原链接，不用假任务填充。

## 三条具体路径

**用户反馈：** 在 vLLM/SGLang 报告中发现难以理解的引用 → 进入共建社区 → 选择“反馈体验” → 查看 #35 是否已有相同问题 → 复制说明草稿并打开 GitHub，由用户检查后提交 → 在原讨论追踪修复 → 点击发布记录回到案例复验。

**资料贡献：** 发现新版官方能力说明 → 贡献资料 → 填来源与受影响对象 → 选择纠错或资讯提交 → 独立审核 → 合入版本化资料 → 下一次研究使用新资料。既有报告不自动改写，新旧依据分别保留；资料版本化自动更新不属于首版实现。

**开发协作：** 阅读小范围需求 → 搜索关联 issue/PR 和负责人 → 在已有线程说明意图与验收 → 人或获授权的 Agent 实现 → PR 附测试和披露 → 维护者评审发布 → 用户复验。提交需求不会自动启动 Agent，也不意味着任务被接受。

## 闭环与数据最小化

闭环为：使用发现问题 → 证据化反馈 → 去重与定范围 → 实现/资料审核 → 发布 → 返回原场景验证。来源、知识、报告和社区各有职责；公共贡献不等于把私人知识库公开。

首版可设计“复制反馈摘要”，字段只含用户选择公开的模块、对象或来源标识、可复现 URL、产品版本、问题说明。必须提供预览与编辑，不自动带入报告正文、笔记、凭据、对话或本机存储。使用 GitHub 提交需要其账户；未登录仍可浏览文档并复制草稿，不能显示“已提交”。用户确认提交后才有真实 GitHub 记录。

沿用已有需求、缺陷、体验、数据纠错、事件表单，不再建立重复入口。来源页面、issue 和 PR 均为资料，不是权限；`event-approved` 由独立内容审核控制，不能因为提交或开发验收而自动添加。许可、产品方向和商业承诺仍由维护者决定。

## 公共与商业的分工

X-lab 的公共入口承接开放资料、方法、反馈和协作。机构定制研究、共享工作区、服务交付等需求单独讨论，由 OpenShare 商业运营承接的具体安排需另行确认。首版不假装已有支付、账户互通、Token 权益或服务 SLA；合作入口不替代产品反馈，也不影响自然排序、数据或研究结论。不公开客户私密需求。

## 实施切分与验收

**第一步：导航与协作入口。** 将可见名称改为共建社区，保留 `#contribute` 兼容；实现三个意图入口、相关说明和既有 GitHub 链接。来源：`src/observatory/portal.ts`、导航名称定义、共享样式。保留敏感报告入口和原有协作内容，移除已过时的“当前交付”硬编码。

**第二步：显式反馈衔接。** 从阅读、知识与报告增加轻量反馈入口及可编辑摘要。只传用户选择的公开上下文；不自动发布，不建立云端存储。需要独立验证跨模块状态保持与长内容布局。

**第三步：发布回访。** 有真实记录后再增加精选成果清单。以后若展示任务状态，须先建设带核对时间、失败/过期状态和维护责任的数据接口；不能把构建时快照称为实时状态。

首版验收：

- 新用户在一屏内找到三种贡献意图，两个动作内抵达相应已有讨论、表单或指南。
- 中文/英文、明暗主题、键盘焦点、390px 手机无横向溢出；主导航和原路由可返回。
- 反馈草稿不会未经操作上传；未提交、打开 GitHub、真实提交三种状态不混淆。
- 每条成果链接到实际 PR/部署证据；没有虚构用户、任务或背书。
- 情报室资料选择、笔记和报告不因导航或反馈被重置。

第一版评审问题：用户是否能说清下一步、是否会担心自己的笔记被公开、是否能返回原使用场景验证改进。尚无埋点或使用统计，不能推算转化率。后续观察需明确同意与数据范围。

## English summary

Proposed navigation name: **Community** (共建社区), replacing the visible Contribute label while keeping `#contribute`. Three intent-based entries—feedback, evidence contribution, development—lead to existing GitHub discussions, forms and guidance. A compact action area and explanation panel replace a generic promotional page. Reviewed changes link back to product use. No automatic posting, agent dispatch, public notebook sharing, live task status, billing or invented activity is implied. This document is a design proposal only.
